1 INTRODUÇÃO

Este documento apresenta o projeto de banco de dados desenvolvido pela Equipe Cortex para a disciplina de Banco de Dados I (BRABCD1) do curso de Tecnologia em Análise e Desenvolvimento de Sistemas do Instituto Federal de Educação, Ciência e Tecnologia de São Paulo, Câmpus Bragança Paulista, como parte do Projeto Interdisciplinar (INSTITUTO FEDERAL DE EDUCAÇÃO, CIÊNCIA E TECNOLOGIA DE SÃO PAULO, 2026).

O banco modela parte do Sistema de Gestão de Demandas de Articulação, que a equipe desenvolve para o CRIE (Centro de Integração Especial, ligado à APAE de Extrema/MG) no âmbito do projeto de extensão “Sistemas em Ação: Desenvolvimento de Soluções Digitais para Demandas Comunitárias”, da disciplina Extensão como Metodologia de Ensino 2 (BRAEXT2). O objetivo do trabalho é modelar, implementar e consultar um banco de dados relacional para o recorte central desse sistema, com seis tabelas, relacionamentos dos tipos 1:1, 1:N e N:N e dados fictícios, com base na bibliografia da disciplina (HEUSER, 2000; ELMASRI; NAVATHE, 2002). 2 UNIVERSO DE DISCURSO

O universo de discurso a seguir resume o minimundo especificado pela equipe (EQUIPE CORTEX, 2026).

O CRIE (Centro de Integração Especial, ligado à APAE de Extrema/MG) atende pessoas com deficiência e organiza seus atendimentos em três setores: pedagógico, saúde e serviço de convivência. Cada setor realiza uma reunião semanal de equipe, na qual são discutidas as situações dos assistidos que não puderam ser resolvidas só com os recursos internos da instituição. De cada reunião registram-se a data, o setor que a realizou e o momento do registro.

Nas reuniões são levantadas demandas de articulação: situações que exigem providências com profissionais da instituição, famílias ou serviços da rede pública (CRAS, unidades de saúde, escolas, Conselho Tutelar). Cada demanda nasce em uma única reunião, e uma reunião pode originar várias demandas ou nenhuma. De cada demanda registram-se a descrição, a categoria, a prioridade (baixa, média ou alta), o prazo, o estado e os momentos de criação e da última atualização. O estado assume apenas os valores aberta, em andamento, aguardando terceiros, concluída ou cancelada; toda demanda nasce aberta, e as concluídas ou canceladas são consideradas encerradas. Cada demanda tem um único profissional responsável e pode se referir a no máximo um assistido, ou a nenhum, nos casos institucionais.

Os profissionais e a direção acessam o sistema como usuários. De cada usuário registram-se o nome, o e-mail (único), a senha, guardada apenas na forma de hash, o perfil (direção, assistente social ou equipe pedagógica), se está ativo e a data de cadastro. Usuários não são excluídos, apenas desativados, para preservar a autoria dos registros antigos.

Dos assistidos registram-se apenas o nome de tratamento, a situação (ativo ou não) e a data de cadastro, seguindo o princípio da minimização de dados da LGPD. Um assistido pode ser acompanhado por vários profissionais, e cada profissional pode acompanhar vários assistidos; desse vínculo registra-se a data de início.

Por fim, os profissionais registram evoluções: anotações sobre o acompanhamento de um assistido, com data, área de atuação, descrição e o momento do lançamento. Cada evolução pertence a um único assistido e a um único profissional. Uma evolução nunca é apagada nem alterada: para corrigi-la, lança-se uma nova versão que aponta para a versão corrigida. Cada versão pode ser retificada no máximo uma vez, o que forma uma cadeia de versões.

Todos os dados usados nesta entrega são fictícios, como exige o minimundo do projeto.

2.1 Recorte implementado

O sistema completo, descrito no minimundo e no DER da equipe, tem 12 entidades. 4.2 Verificação das formas normais

A verificação considerou a primeira, a segunda e a terceira formas normais, vistas na Aula 09.

1FN: todos os atributos são atômicos e não há grupos repetidos. Os vários profissionais de um assistido não ficam numa lista dentro de ASSISTIDO: viram linhas da tabela associativa ASSISTIDO_PROFISSIONAL.

2FN: a única chave primária composta é a de ASSISTIDO_PROFISSIONAL (assistido_id, profissional_id), e seu único atributo, data_inicio, depende da chave inteira: é a data em que aquele profissional começou a acompanhar aquele assistido. Nas demais tabelas a chave é simples, então não há dependência parcial.

3FN: não há dependência transitiva. O setor da demanda não é guardado em DEMANDA, porque é determinado pela reunião (reuniao_id determina setor); ele é obtido pela junção, como na consulta Q09. Nome e perfil do responsável ficam só em USUARIO. Não há campos calculados: dias de atraso, idade do acompanhamento e médias são calculados nas consultas.

6.3 Consulta Q03: demandas em aberto com prazo vencido

Objetivo: Demandas em aberto com o prazo vencido e há quantos dias estão atrasadas, da mais atrasada para a menos atrasada.

Comandos usados: CURDATE, DATEDIFF, NOT IN, ORDER BY DESC.

O Código 3 apresenta a instrução SQL, e a Tabela 4, o resultado obtido, com 6 linhas.

Código 3 – Consulta Q03

SELECT id,
descricao,
estado,
DATE_FORMAT(prazo, '%d/%m/%Y') AS prazo,
DATEDIFF(CURDATE(), prazo) AS dias_de_atraso
FROM demanda
WHERE estado NOT IN ('concluida', 'cancelada')

O Código 17 apresenta a instrução SQL, e a Tabela 18, o resultado obtido, com 13 linhas.

Código 17 – Consulta Q17

SELECT r.id AS reuniao,
r.setor,
DATE_FORMAT(r.data, '%d/%m/%Y') AS data,
COUNT(d.id) AS demandas_originadas
FROM demanda d
RIGHT JOIN reuniao r ON r.id = d.reuniao_id
GROUP BY r.id, r.setor, r.data
ORDER BY r.data;

USUARIO: profissional ou membro da direção que acessa o sistema.

REUNIAO: reunião semanal de um setor (RN01).
O setor é um domínio fechado de três valores.
--------------------------------------------------------------------- */
CREATE TABLE reuniao (

data DATE NOT NULL,
setor ENUM('pedagogico', 'saude', 'convivencia') NOT NULL,
criado_em DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

);

DEMANDA: situação levantada em reunião que exige articulação.
Estado em domínio fechado (RN05) e sempre nasce 'aberta' (RN06).
--------------------------------------------------------------------- */

id INT NOT NULL AUTO_INCREMENT,
descricao TEXT NOT NULL,
categoria VARCHAR(80) NULL,
prioridade ENUM('baixa', 'media', 'alta') NOT NULL,
prazo DATE NOT NULL,
estado ENUM('aberta', 'em_andamento', 'aguardando_terceiros', 'concluida', 'cancelada')
NOT NULL DEFAULT 'aberta',
responsavel_id INT NOT NULL, -- 1:N com USUARIO (é responsável por)
reuniao_id INT NOT NULL, -- 1:N com REUNIAO (origina)
assistido_id INT NULL, -- 1:N opcional com ASSISTIDO (RN03)
criado_em DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
atualizado_em DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
PRIMARY KEY (id),
FOREIGN KEY (responsavel_id) REFERENCES usuario (id) ON UPDATE CASCADE,
FOREIGN KEY (reuniao_id) REFERENCES reuniao (id) ON UPDATE CASCADE,
FOREIGN KEY (assistido_id) REFERENCES assistido (id) ON UPDATE CASCADE
);

EVOLUCAO: anotação de acompanhamento do assistido, feita por um profissional.
Não é apagada nem editada: corrigir é lançar uma nova versão que aponta
para a original (retifica_id). O UNIQUE em retifica_id faz o
autorrelacionamento ser 1:1: cada versão é retificada no máximo uma vez.
--------------------------------------------------------------------- */
CREATE TABLE evolucao (
id INT NOT NULL AUTO_INCREMENT,
assistido_id INT NOT NULL, -- 1:N com ASSISTIDO (possui)
profissional_id INT NOT NULL, -- 1:N com USUARIO (escreve)
data DATE NOT NULL,
area_atuacao VARCHAR(80) NOT NULL,
descricao TEXT NOT NULL,
ocorrido_em DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
retifica_id INT NULL, -- 1:1 com a própria EVOLUCAO (retifica)
PRIMARY KEY (id),
FOREIGN KEY (assistido_id) REFERENCES assistido (id) ON UPDATE CASCADE,
FOREIGN KEY (profissional_id) REFERENCES usuario (id) ON UPDATE CASCADE
);
 
-- A chave do autorrelacionamento é acrescentada com ALTER TABLE:
-- UNIQUE garante o 1:1 e a FOREIGN KEY garante que a versão retificada existe.
ALTER TABLE evolucao
ADD CONSTRAINT uq_evolucao_retifica UNIQUE (retifica_id),
ADD CONSTRAINT fk_evolucao_retifica FOREIGN KEY (retifica_id)
REFERENCES evolucao (id) ON UPDATE CASCADE;
 
-- Conferência da estrutura criada
SHOW TABLES;
DESCRIBE demanda;
DESCRIBE evolucao;
